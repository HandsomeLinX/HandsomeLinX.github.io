UNITY WEBGL · H5 BUILD

Unity WebGL 溝通知識地圖

給介於工程師實作與上層之間的溝通者。目標是聽得懂、能判斷影響、問得對問題，不是會做。內容分三塊：工程師提出的三項建議、交界處的全局知識、知識深度要學到哪裡。

一工程師的三項建議

1　編譯產物與用途

.wasm 是程式，.data 是首包資源，其他是載入和溝通的工具。玩家首次進入要等首包全部下載完。

檔案是什麼需要知道的影響
index.html + TemplateData/網頁外殼（載入畫面、進度條、樣式）可客製；平台嵌入、品牌 Loading 頁改這裡
xxx.loader.js啟動器，負責下載、解壓其他檔案並啟動遊戲很小，通常不用管
xxx.framework.jsJS 膠水碼，讓 wasm 能呼叫瀏覽器功能（音效、輸入、網路）自寫的 .jslib（跟網頁／平台溝通的橋）會編進這裡
xxx.wasmC# 程式碼 + Unity 引擎，經 IL2CPP 轉成 WebAssembly程式碼量、引擎模組、剝離設定決定大小
xxx.data首包資源：場景、Resources、內建素材、Shader放越多，玩家越久才看到畫面
StreamingAssets/原樣複製的檔案，執行時用網址下載不進首包，按需讀取
.symbols.json（選用）除錯符號只給開發用，不該上正式環境
AssetBundle / Addressables動態下載的資源包必須針對 WebGL 平台重新 build，不能沿用 Android/iOS 的包

2　影響首包大小與效能的設定

設定分三類：影響程式碼、影響資源、影響傳輸。每一項都是取捨，沒有單一最佳值。

影響 .wasm 的設定

  • Managed Stripping Level（託管程式碼剝離）：刪掉沒用到的 C# 程式碼。等級越高越小，但可能誤刪靠反射呼叫的程式碼（JSON 序列化、某些第三方套件），執行時才報錯。調高後要完整回歸測試。
  • Strip Engine Code：刪掉沒用到的 Unity 引擎模組，例如沒用物理就不包物理。
  • IL2CPP Code Generation：「執行速度優先」或「檔案較小、編譯較快」二選一。
  • WebAssembly 版本／語言特性（名稱依 Unity 版本而異）：較新的 wasm 特性（SIMD、原生例外處理）效能通常更好、檔案可能更小，但舊瀏覽器、舊 iOS 可能跑不動。要對照目標市場裝置分佈決定。
  • Exception Support：全開利於除錯但檔案大、效能差，正式版通常只保留最低限度。
  • 程式碼本身：大型第三方套件、大量泛型都會讓 wasm 膨脹。

影響 .data 的設定

  • Build 包含的場景、Resources 資料夾內容。Resources 裡的東西不管有沒有用都會被包進去，是常見的肥大來源。
  • 貼圖壓縮格式與尺寸、音效壓縮。
  • Shader 變體數量。變體太多會讓首包變大、載入變慢。

影響傳輸的設定

  • Compression Format（Brotli / Gzip / 不壓縮）：Brotli 最小，但需要伺服器正確設定（見第二部分 A）。

3　WebGL 版本差異、載體相容與特效影響

H5 版特效可能需要一套獨立標準，不能直接沿用 App 版。

  • WebGL 2.0 大致等同手機的 OpenGL ES 3.0。新版 Unity 已不支援 WebGL 1.0。
  • WebGPU 是下一代標準，新版 Unity 有實驗性支援，能用 Compute Shader，但瀏覽器支援度仍在擴展中，目前不適合當主要方案。

WebGL 2.0 對特效的限制

限制實際影響
沒有 Compute Shader依賴 GPU 運算的粒子（VFX Graph）基本不能用，要改用傳統 Particle System
沒有 Geometry Shader部分進階 Shader 效果不能用
多執行緒受限C# Thread 不能照原生方式用，CPU 重運算會卡主線程
後處理成本高Bloom、模糊等全螢幕效果在手機瀏覽器上很吃效能
貼圖壓縮格式分裂桌機用 DXT、手機用 ETC2/ASTC，選錯會在該裝置上解壓變慢、吃記憶體

載體差異

對 RPG 的意義：Spine 骨骼動畫在 WebGL 上可正常運作，但大量同屏動畫、大張 atlas 會直接衝擊記憶體。

二全局更該知道的知識

H5 是 Unity 產物、網頁、伺服器、平台的組合。溝通代溝通常發生在這些交界處，而不是 Unity 內部。

A　部署與伺服器（最常被忽略、最常出事）

  • Brotli 需要 HTTPS，伺服器要回傳正確的 Content-Encoding 標頭；設定錯誤會載入失敗或變得很慢。
  • .wasm 要用正確的 MIME 類型（application/wasm），否則瀏覽器無法串流編譯。
  • CDN：靜態檔案放 CDN，讓各市場玩家就近下載；跨台灣、東南亞、日本等地區，節點分佈很重要。
  • 快取與版本控管：檔名帶 hash（Unity 的「Name Files As Hashes」選項），更新後玩家不會卡在舊快取，與 App 的 AB 版本管理是同類問題。
  • CORS：遊戲、資源、API 放在不同網域時需設定跨域許可，否則請求會被瀏覽器擋下。

「帳號」類困擾多屬於這一塊：網域、SSL 憑證、CDN、雲端儲存、DNS。建議整理一張對照表：

服務用途負責人帳號持有者
網域／DNS玩家連到哪個網址
SSL 憑證HTTPS，Brotli 的前提
CDN各市場就近下載
雲端儲存存放 build 產物與資源包

B　載入體驗（玩家實際感受到的）

  • 首包大小約等於流失率。業界常見目標是首包控制在數十 MB 內，手機越小越好，具體門檻依平台決定。
  • 策略：首包只放「進主城」需要的東西，各地圖用 AssetBundle / Addressables 按需下載，與 App 分包思路相同。
  • 瀏覽器快取（IndexedDB）：Unity 可把下載過的檔案存起來，第二次進入快很多；但 iOS 可能清掉這些快取。

C　記憶體（H5 最大的技術風險）

  • WebGL 記憶體是一塊預先配置、可成長的區域，手機瀏覽器能給的上限遠低於 App。
  • 真正吃記憶體的是解壓後的貼圖、音效、Spine，不只是檔案大小。
  • 可要求工程師提供：各地圖峰值記憶體、iOS 最低支援機型的實測結果。

D　與網頁外殼、平台的溝通

  • 遊戲與網頁（登入、儲值、分享、關閉）透過 JS Bridge（.jslib）溝通。這是與平台方、Web 前端最容易對不上的地方，介面規格要寫成文件。
  • 嵌在別人頁面裡（iframe）時，會有權限、全螢幕、音效的額外限制。

E　瀏覽器政策限制

  • 自動播放政策：玩家第一次點擊前不能播音效，登入後的主城 BGM 要設計成點擊後才播。
  • 全螢幕、橫豎屏：iOS Safari 對全螢幕支援有限，橫屏遊戲體驗要另外規劃。
  • 背景分頁：切到其他分頁時遊戲會被降速或暫停，連線、計時邏輯要能處理。

三深度邊界與 build 回報清單

核心層是 L2「因果與取捨」：決策發生在這裡，實作交給工程師。

判斷法：這件事會不會讓我做出不同的決策、或擋下一個風險？會，就學到 L2；不會，停在 L1。

每次 build 要工程師回報的數字

有了這張表，不需要懂實作，也能追蹤趨勢、發現異常、與上下對齊。

  1. 首包各檔案大小（wasm / data / framework）
  2. 首次載入時間與二次載入時間（指定目標機型、網速）
  3. 峰值記憶體（iOS 最低機型）
  4. 目前的 Stripping、壓縮、wasm 特性設定
  5. 已知的不支援裝置／瀏覽器清單
